The decision in one figure

A breakdown that only one threshold caught

Machine MCH-213 failed at 18:00 on 8 April. The model had been watching it all along — but whether anyone was told came down to where the alert line sat. At 0.30 the warning never fires. At 0.20 it fires 22 hours ahead, with a peak score of 0.2247: a margin of about two hundredths.

Why the headline metric chose wrong

164 “failures” in the test set are really 7 breakdowns

Each failure is expanded into a 24-hour warning window, so one breakdown becomes roughly 24 positive machine-hours. Row-level scoring counts those hours. Judged that way, Logistic Regression looks decisively safer at threshold 0.5 — 2 missed hours against Random Forest's 49.

But missing 49 hours of a 24-hour window says nothing about whether the plant was warned. Re-scored on what operations actually experiences — did any alert fire before each real breakdown, and how many separate false alarms did operators have to chase — the ranking inverts.

The decision needs no cost assumptions

Normally this call means pricing unplanned downtime against an unnecessary inspection — a ratio this dataset does not contain, and one that is not invented here. It isn't needed. Random Forest is better on both axes at once: more breakdowns caught and fewer false alarms. When one option dominates, the exchange rate between the two costs is irrelevant — every ratio returns the same answer.

Candidate comparison

Six models, three windows, no winner without the numbers

The raw positive rate is 0.039%. A model that never alerts scores 99.96% accuracy and is worthless, so accuracy and ROC are both dishonest here. AUC-PR ignores true negatives entirely, and its no-skill floor is the positive rate itself — an honest baseline to beat.

Three results worth stating plainly

  • Boosting did not help. HistGradientBoosting and XGBoost trail Random Forest on all three windows. Further variants were deliberately not added — with 164 positive test rows, more candidates buy noise, not signal.
  • No stacked ensemble was built. With 17 real failure events a trained meta-learner would fit which model got lucky on which breakdown. The two training-free combinations tested lose to the best single model on two of three windows, and majority vote is worst of all — binarising at 0.5 before combining discards exactly the ranking information AUC-PR rewards.
  • The interpretable model is the unstable one. At 0.0301 on fold 1, Logistic Regression sits barely above the 0.0086 naive floor. Trained on the least data, it essentially stops working — which matters, because this system is retrained as history accumulates.
Operating point

Why the alert line sits at 0.20

Dropping from 0.30 to 0.20 converts a missed breakdown into a caught one while the false-alarm episode count stays flat — 23 down to 22. The extra alert hours land inside warning windows that were already firing, so operators see no additional noise.

Risk drivers

Instability predicts failure — not temperature

Rolling standard deviations alone carry 63.5% of total feature importance; raw instantaneous readings contribute under 8% combined. Machines here don't fail because they run hot — they fail because they start running erratically. Vibration outweighs temperature roughly 62% to 37%.

The most important number here is the smallest one

run_hours_since_maintenance contributes 0.007. The intuitive “wear since last service” hypothesis is not what drives these predictions — and that is a quiet vindication of the leakage guard. Restricted to causal use the feature is nearly worthless; a forward-looking version would have looked spectacularly predictive by encoding the reactive maintenance reset that follows the breakdown. Production line contributes 0.0006, which strengthens the cold-start case: the model leans on no plant topology it cannot verify for a new machine.

Validation design

How the evaluation was kept honest

Time-ordered splits, never random k-fold

Hourly readings within a machine are strongly autocorrelated, so random k-fold would leak neighbouring hours across the split and inflate every score. A third fold trained on January alone was deliberately not used — January contains zero failures, so there would be no positive class to fit against.

A 24-hour embargo on the target

The label at time t depends on data up to t+24h, so a training row within 24 hours of the cutoff has a label partly determined by test-side data — leakage through the target, which no amount of careful feature engineering would catch. Every split purges training rows whose horizon window crosses its cutoff.

Causality proven, not promised

77.3% of maintenance resets coincide with or immediately follow the breakdown they would appear to predict — resets are largely reactive. A forward-looking feature built on them would be a near-copy of the label. So every feature is recomputed on truncated data and asserted unchanged: a feature that peeks forward changes when the future is removed.

$ python src/test_no_leakage.py OK: all 19 features are causal (unchanged across 25926 rows when future data is truncated).

Cold-start machines are excluded, but still scoreable

MCH-300 and MCH-301 hold 72 rows each — 2.96 days, zero failures. Three days cannot support a 24-hour horizon label, so both are excluded from training and evaluation. So that they remain scoreable, machine_id is deliberately not a feature: the model reads only physically-grounded signals and generalises to machines it has never seen. Their scores are real predictions but unvalidated.

Limitations

What this evidence does not establish

Sample size 19 events is small. 19/19 is a real result over ~83 days of held-out testing, not a guarantee. It should be described to the plant team as “caught every failure in testing” — never as “never misses”.
Alarm precision Roughly 3 of every 4 alert episodes are false (row-level precision 0.378). Acceptable given the cost asymmetry, but the plant team must be told upfront so the expectation is calibrated from day one.
Cold start MCH-300 and MCH-301 are unvalidated, not validated-good. With zero recorded failures their event-level recall is unmeasurable. Their dashboard scores need a visible lower-confidence marker.
Trend view Historical scores in the app will be in-sample. The shipped artifact is refit on all established history, so re-scoring that same history produces optimistic risk curves. The trend chart needs walk-forward out-of-sample scores instead.
Missing data Forward-fill is justified only by this dataset's gap profile — ~99% of gaps are isolated single hours, longest run 2. A future feed with real outages would need this revisited.
Failure modes Failures are near-uniform across machines (1–2 each), so the model cannot learn machine-specific failure modes — by design, since that is also what lets it score new machines.
